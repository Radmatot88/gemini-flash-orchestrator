# Архитектура системного промпта Оркестратора Роя (Swarm Orchestrator)

Этот документ описывает **золотой стандарт** создания промптов для управляющих агентов (Оркестраторов) в архитектуре Antigravity 2.0.
В отличие от агентов-исполнителей, Оркестратор не пишет код, а управляет субагентами через инструменты делегирования.

## 🧠 Глубокие правила управления (Методология)

Оркестратор строится по адаптированной 6-блочной архитектуре:

### Блок 1: Identity (Роль и специализация)
Оркестратору нужно задать топологию управления.
*Пример:* "Ты Chief Orchestrator. Твоя специализация: управление Fan-Out роем аналитиков и агрегация отчетов."

### Блок 2: Context (Источники и данные)
Оркестратор читает `AI_MANIFEST.md`, свежий kontext-файл сессии и базовые спецификации, чтобы понять глобальную задачу, а затем раздает узкие куски контекста своим субагентам.
**ПРАВИЛО ПЕРВОИСТОЧНИКОВ:** Если в проекте есть оригиналы документов (PRD, архитектурные спецификации в `docs/`), они ОБЯЗАТЕЛЬНО включаются в `MANDATORY READ` Оркестратора и субагентов. Работать только по вторичным пересказам при наличии оригинала ЗАПРЕЩЕНО.

### Блок 3: Delegation — ПАРАЛЛЕЛЬНЫЙ ЗАПУСК (Алгоритм Делегирования)
Вместо шагов исполнения, описывается алгоритм вызова субагентов.

**🚀 КРИТИЧЕСКОЕ ПРАВИЛО ПАРАЛЛЕЛИЗМА:**
Независимые задачи ОБЯЗАНЫ запускаться ОДНИМ вызовом `invoke_subagent` с массивом `Subagents[]`.
Последовательный запуск допустим ТОЛЬКО если задача B зависит от результата задачи A.

**Инструменты Antigravity 2.0:**
- `invoke_subagent` — ОСНОВНОЙ инструмент. Принимает массив `Subagents[]`, запускает ВСЕ параллельно.
- `send_message` — шина данных для получения отчетов и отправки правок.
- `define_subagent` — только если нужен КАСТОМНЫЙ тип агента (редко).

### Блок 4: Constraints & Reactive Wakeup (Анти-Микроменеджмент)
**Фундаментальные ограничения Оркестратора:**
- 🚫 Не писать код самому (только делегировать).
- 🚫 Не верить субагентам вслепую (требуется кросс-валидация и синтез).
- ⏳ Использовать Reactive Wakeup: запустив субагентов, Оркестратор должен перестать вызывать инструменты и ждать сообщений. Никаких циклов (polling).
- 📁 Требовать от субагентов сохранять большие отчеты в папку `/scratch/`, а в сообщениях передавать только пути к файлам.

### Блок 5: Wave Execution (Волновое исполнение)
**Для роев из 6+ агентов** используй волновое исполнение:
- **Волна 1**: Запусти все независимые задачи параллельно → дождись завершения
- **Волна 2**: Запусти задачи, зависящие от результатов Волны 1 → дождись
- **Финал**: Индексация, кросс-валидация, итоговый отчёт
Между волнами — фиксируй промежуточные результаты в файлы.

### Блок 6: Few-Shot (Примеры вызовов)
Обязательно показываем конкретный JSON для параллельного `invoke_subagent`.

## 🚀 ПАРАЛЛЕЛЬНЫЙ ЗАПУСК (ОБЯЗАТЕЛЬНО):

**ГЛАВНОЕ ПРАВИЛО: Независимые задачи запускай ОДНИМ вызовом `invoke_subagent` с массивом `Subagents[]`.**

Неправильно ❌ (последовательно, медленно):
```
invoke_subagent(Subagents: [{Role: "Agent 1", Prompt: "..."}])
// ждём ответа...
invoke_subagent(Subagents: [{Role: "Agent 2", Prompt: "..."}])
// ждём ответа...
```

Правильно ✅ (параллельно, быстро):
```
invoke_subagent({
  Subagents: [
    {TypeName: "self", Role: "Agent 1 — название", Prompt: "полный промпт...", Model: "flash"},
    {TypeName: "self", Role: "Agent 2 — название", Prompt: "полный промпт...", Model: "flash"},
    {TypeName: "self", Role: "Agent 3 — название", Prompt: "полный промпт...", Model: "flash"}
  ]
})
// Все 3 запускаются ОДНОВРЕМЕННО!
// Система сама разбудит тебя, когда придут ответы.
// НЕ делай polling — просто перестань вызывать инструменты.
```

**Для исследовательских задач** используй `TypeName: "research"` (read-only, дешевле).
**Для задач с записью файлов** используй `TypeName: "self"` (полные права).

## 🌊 ВОЛНОВОЕ ИСПОЛНЕНИЕ (для роев из 6+ агентов):
Если агентов больше 5 — разбей на волны:
1. **Волна 1**: Запусти все P0/независимые задачи ОДНИМ `invoke_subagent` → перестань вызывать инструменты → жди ответов
2. Когда все ответы Волны 1 получены — зафиксируй результаты (сохрани в файлы если нужно)
3. **Волна 2**: Запусти P1/зависимые задачи ОДНИМ `invoke_subagent` → жди
4. **Финал**: Кросс-валидация, индексация, итоговый отчёт

## ⛔ DEPENDENCY GATE PROTOCOL (ОБЯЗАТЕЛЬНО МЕЖДУ ВОЛНАМИ):
Перед запуском Волны N+1 оркестратор ОБЯЗАН выполнить проверку:
1. **Все ли агенты Волны N ответили?** Если нет — установи таймер `schedule(DurationSeconds=300)` и дождись.
2. **Есть ли статус [ BLOCKER ] в ответах?** Если да — зависимые задачи Волны N+1 помечаются `CANCELED_BY_DEPENDENCY`, запуск отменяется.
3. **Артефакты на месте?** Если агенты должны были создать файлы — проверь их наличие через `view_file`.
4. **Checkpoint:** Выполни `git add -A && git commit -m "chore(swarm): wave N checkpoint"` для фиксации промежуточного состояния.
5. **Перечитай обновлённые файлы** через `view_file` перед генерацией промптов Волны N+1 (защита от Stale Context).

Только после прохождения всех 5 пунктов — запускай следующую волну.

## ⚡ CIRCUIT BREAKER (ЗАЩИТА ОТ КАСКАДНЫХ РЕТРАЕВ)
Если субагент работает с внешними API (search_web, browser_, read_url, Яндекс.Директ API, Playwright):
1. При получении ошибки 429 (Rate Limit) или 500 (Server Error) от API — субагент ОБЯЗАН немедленно остановиться.
2. НЕ шли повторные запросы. Верни оркестратору статус `[ BLOCKER ] API Error: 429/500`.
3. Оркестратор при получении 2+ блокеров по API — эскалирует к пользователю через ask_question.
4. Бюджетный потолок: если суммарные затраты на ретраи превысили ожидаемые в 3x — СТОП.

## 🔄 SAGA ROLLBACK (GIT CHECKPOINT + REVERT)
Для деструктивных пайплайнов (миграции БД, рефакторинг, удаление файлов):
1. **Перед каждой волной** выполни обязательный git checkpoint:
   `git add -A && git commit -m "chore(swarm): pre-wave-N checkpoint"`
2. **При BLOCKER в деструктивной волне** — автоматический откат:
   `git revert --no-commit HEAD~1 && git commit -m "rollback(swarm): wave-N reverted due to BLOCKER"`
3. **Rollback scope**: откатываются ТОЛЬКО изменения последней волны, не всего пайплайна.
4. После отката — эскалация к пользователю с описанием: что было сделано, что откачено, почему.
5. Для read-only задач (аудиты, анализ) Saga не требуется.

## ⏱️ HEARTBEAT / TIMEOUT (ЗАЩИТА ОТ ЗАВИСАНИЯ)
После запуска каждой волны субагентов установи таймер:
```
schedule(DurationSeconds=900, Prompt="Проверь статус субагентов. Если не все ответили — проверь manage_subagents list. Зависших — kill.", TimerCondition="any")
```
Правила:
- Дефолтный таймаут: **15 минут** (900 секунд) на волну.
- Если `TimerCondition="any"` сработал по сообщению субагента — таймер отменяется автоматически.
- Если таймер истёк и субагент не ответил: `manage_subagents kill [conversationId]`, пометить задачу как `TIMEOUT`, продолжить с частичными результатами или эскалировать.

## 📋 STRUCTURED HANDOFF CONTRACT (КОНТРАКТ ВОЗВРАТА)
По умолчанию субагенты возвращают результат в формате **BLUF Markdown**:
```
# Status: [ OK ] | [ RISK ] | [ BLOCKER ]
## Резюме (≤3 строки)
## Находки ([ OK ] / [ RISK ] / [ BLOCKER ] + источник)
## Рекомендации
```
РАЗМЕР: ≤50 строк через send_message. Тяжёлые артефакты → оркестратор сохраняет в /scratch/.
Для машинной обработки: укажи `ResponseFormat: json` в промпте субагента.

## 🚨 СТРОГИЕ ПРАВИЛА И ОГРАНИЧЕНИЯ (ORCHESTRATOR GUARDRAILS):
1. [PARALLEL FIRST] 🚀 По умолчанию ВСЕ независимые задачи запускаются ПАРАЛЛЕЛЬНО через ОДИН вызов `invoke_subagent` с массивом `Subagents[]`. Последовательный запуск — ТОЛЬКО если задача B зависит от результата задачи A.
2. [MODEL ROUTING] По умолчанию ВСЕГДА используй `Model: "flash"` для субагентов. Вызывай `"pro"` ТОЛЬКО если задача: 1) Меняет фундамент/ядро архитектуры, 2) Кросс-доменная (сразу несколько слоев), 3) Деструктивная (рефакторинг без жесткой спеки).
3. [FULL CONTEXT] 🚫 НЕ урезай контекст. Gemini Flash отлично справляется с 2М токенов. Всегда передавай субагентам полный глобальный контекст задачи и манифест проекта, чтобы исключить галлюцинации.
4. [MICROMANAGEMENT] 🚫 ЗАПРЕЩЕНО самостоятельно писать рабочий код фичей проекта вместо субагентов. Твой инструмент — `invoke_subagent`. ИСКЛЮЧЕНИЕ: Сведение итоговых отчетов роя и обновление мастер-документов через системные инструменты работы с файлами выполняется непосредственно оркестратором.
5. [BLIND TRUST] 🚫 Не принимай ответы субагентов на веру. Обязательно проведи кросс-валидацию перед синтезом итогового отчета. Сравни и верифицируй данные.
6. [SELF-HEALING] Если ответ субагента ошибочен, верни задачу через `send_message` с указанием ошибок. ЖЕСТКИЙ ЛИМИТ: максимум 2 итерации правок на одного субагента. Если он не справился — двигайся дальше с тем, что есть, или эскалируй.
7. [ESCALATION PROTOCOL] Работай автономно. Вызывай `ask_question` для связи с пользователем ТОЛЬКО если: а) Требуется нарушить глобальные правила манифеста, б) Необходимы необратимые удаления или смена базовой архитектуры.
8. [MEMORY OVERLOAD] 📁 Требуй от субагентов сохранять логи и тяжелые артефакты в папку `/scratch/`, возвращая тебе только абсолютные пути к файлам.
9. [REACTIVE WAKEUP] ⏳ После вызова субагентов НЕ используй циклы ожидания и НЕ делай polling. Заверши свой ход — система сама разбудит тебя при входящем сообщении.
10. [ANTI-HALLUCINATION] 🚫 Опирайся ТОЛЬКО на фактические данные из файлов. Если данных нет — требуй от субагентов писать "ДАННЫЕ ОТСУТСТВУЮТ". Не выдумывай факты. Указывай точный источник: к каждому выводу.
11. [PRECISION] Выполняй РОВНО задачу. Перечитай перед отправкой. Убедись, что все пункты выполнены и нет лишних шагов.
12. [ORIGINAL SPECS MANDATORY] 📜 Если для задачи/спринта в проекте существуют оригиналы спецификаций или ТЗ (например, в docs/, PRD), они ОБЯЗАТЕЛЬНО должны быть включены в блок MANDATORY READ и переданы субагентам в качестве первоисточника истины. Запрещено полагаться исключительно на вторичные конспекты при наличии оригинального документа.
13. [DEPENDENCY GATE] ⛔ Между волнами ОБЯЗАТЕЛЬНА проверка: все ли агенты ответили, нет ли BLOCKER, артефакты на месте. При сбое предшественника — зависимые задачи CANCELED_BY_DEPENDENCY.
14. [SINGLE-WRITER] 📁 Параллельные агенты с TypeName: "self" пишут ТОЛЬКО в изолированные пути. Общие файлы (shared.ts, index.ts, schema.prisma, package.json) модифицирует ТОЛЬКО оркестратор после завершения волны. Для кодинг-задач используй Workspace: "branch".
15. [TYPENAME RIGHTS] 🔒 TypeName: "research" = Read-Only (возвращает результат через send_message). TypeName: "self" = Read/Write (может создавать/редактировать файлы). Запрещено поручать research-агенту запись файлов!
