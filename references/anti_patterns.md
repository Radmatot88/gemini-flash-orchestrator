# 12 антипаттернов промптирования Gemini Flash в Antigravity

Каждый антипаттерн содержит: описание проблемы, пример плохого промпта,
правильный подход и уровень критичности.

---

## AP-01: Галлюцинация данных [ CRITICAL ]

**Проблема**: Агент выдумывает факты, цифры или содержимое файлов
вместо того, чтобы прочитать реальные данные.

**Плохо**:
```
Проанализируй юнит-экономику проекта DS Стоматология.
```
Агент «вспомнит» цифры из обучающих данных и выдаст фантазию.

**Хорошо**:
```
📥 ПРОЧИТАЙ: file:///c:/Project/docs/UNIT_ECONOMICS.md
Извлеки из файла: Retainer Fee, расходы на ИИ, трудозатраты.
Каждую цифру сопроводи ссылкой [источник: UNIT_ECONOMICS.md, строка N].
Если данных нет — пиши "ДАННЫЕ ОТСУТСТВУЮТ".
```

---

## AP-02: Хардкод литеральных значений [ CRITICAL ]

**Проблема**: Агент вставляет конкретные даты, суммы или имена из памяти
вместо извлечения из файлов проекта.

**Плохо**:
```
Обнови ROADMAP.md — спринт H1 начинается 4 августа.
```

**Хорошо**:
```
📥 ПРОЧИТАЙ: file:///c:/Project/ROADMAP.md
Найди текущую дату начала спринта H1 в Gantt-диаграмме.
Сдвинь ее на +3 дня. Пересчитай все зависимые даты.
```

---

## AP-03: Неточное исполнение [ HIGH ]

**Проблема**: Агент делает «примерно то, что просили» — добавляет
лишние секции, пропускает пункты или меняет формат.

**Плохо**:
```
Проведи аудит бэкенда.
```
Агент сделает аудит + начнет рефакторить код + напишет тесты.

**Хорошо**:
```
Твоя задача — ТОЛЬКО аудит. Результат — отчет.
1. Прочитай файлы из списка ПРОЧИТАЙ.
2. Для каждого файла проверь: [список критериев].
3. Верни отчет через send_message.
НЕ создавай файлы. НЕ редактируй код. НЕ запускай команды.
Перед отправкой перечитай задачу и убедись: все пункты выполнены,
лишних пунктов нет.
```

---

## AP-04: Негативные промпты без альтернативы [ HIGH ]

**Проблема**: Flash плохо понимает чистое отрицание.
«НЕ ДЕЛАЙ X» часто игнорируется.

**Плохо**:
```
Не отвечай текстом. Не используй эмодзи. Не пиши длинные абзацы.
```

**Хорошо**:
```
ВСЕГДА отвечай вызовом инструмента (tool call).
ВМЕСТО эмодзи используй теги: [ OK ], [ RISK ], [ BLOCKER ].
ВМЕСТО абзацев используй нумерованные списки (макс. 2 строки на пункт).
```

---

## AP-05: Отсутствие контекстного блока [ CRITICAL ]

**Проблема**: Промпт не указывает, какие файлы читать и что создавать.
Агент либо галлюцинирует, либо читает случайные файлы.

**Плохо**:
```
Ты — SEO-аналитик. Проведи аудит сайта.
```

**Хорошо**:
```
📥 ПРОЧИТАЙ:
1. file:///c:/Project/docs/00_PRD.md — бизнес-контекст
2. file:///c:/Project/server/src/modules/seo/ — текущий код SEO

📤 РЕЗУЛЬТАТ:
Файл: file:///c:/Project/docs/seo_audit.md [NEW]

🏷️ РАЗМЕТКА:
- Заголовок: # SEO Audit: [краткий вывод]
- Теги: [ OK ] | [ RISK ] | [ BLOCKER ]
```

---

## AP-06: Универсальный агент (>3 обязанностей) [ HIGH ]

**Проблема**: Один Flash-агент получает задачу «проанализируй + напиши
код + проведи ревью + сгенерируй контент». Flash теряет фокус.

**Плохо**:
```
Проанализируй базу данных, перепиши миграции, проведи код-ревью
и сгенерируй документацию.
```

**Хорошо**: Разбить на 3 агента:
- Агент 1 (flash): Читает schema.prisma → отчет о проблемах
- Агент 2 (pro): Читает отчет Агента 1 → пишет миграции
- Агент 3 (flash): Читает код → генерирует документацию

---

## AP-07: Отсутствие Chain-of-Thought [ HIGH ]

**Проблема**: Flash принимает решения слишком быстро без записи
хода мыслей. Ошибается в 30%+ случаев сложного роутинга.

**Плохо**:
```
Определи, какому агенту делегировать задачу.
```

**Хорошо**:
```
Перед принятием решения ОБЯЗАТЕЛЬНО запиши ход мыслей:
1. Какой тип задачи? (аудит / генерация / анализ / код)
2. Какие файлы нужны?
3. Какая модель подходит? (flash / pro)
4. Вывод: делегирую [агенту X] потому что [причина].
```

---

## AP-08: Глубокая JSON-вложенность (4+ уровней) [ MEDIUM ]

**Проблема**: Flash путает типы данных на 3+ уровне вложенности
(возвращает строку вместо массива).

**Плохо**:
```json
{
  "project": {
    "departments": {
      "seo": {
        "tasks": {
          "audit": { "findings": ["..."] }
        }
      }
    }
  }
}
```

**Хорошо** (плоская структура):
```json
{
  "project_name": "DS Stomatology",
  "department": "seo",
  "task_type": "audit",
  "findings": ["..."],
  "status": "RISK"
}
```

## AP-09: Противоречия в промпте [ HIGH ]

**Проблема**: Flash крайне чувствителен к противоречиям.
Может зациклиться или выдать отказ.

**Плохо**:
```
Отвечай кратко, в 2-3 предложения.
...
Предоставь исчерпывающий детальный анализ с примерами.
```

**Хорошо**: Вычитай промпт на противоречия перед отправкой.
Используй `prompt_validator.py` — он ловит такие паттерны.

---

## AP-10: Отсутствие few-shot примеров [ MEDIUM ]

**Проблема**: Без примеров Flash генерирует непредсказуемый формат.

**Хорошо**: Добавь 2-3 примера идеального ввода-вывода:
```
ПРИМЕР:
Вход: "Проведи аудит schema.prisma"
Выход:
# DB Architect: 3 критических проблемы найдены
## Находки
1. [ BLOCKER ] Отсутствует модель ProjectBlocker [источник: schema.prisma]
2. [ RISK ] Нет поля version для optimistic locking [источник: schema.prisma]
## Рекомендации
1. Добавить модель ProjectBlocker с полями...
```

## AP-11: Слишком длинный промпт без структуры [ MEDIUM ]

**Проблема**: Промпт > 2000 слов в свободной форме (freeform).
Flash «забывает» инструкции в середине текста.

**Хорошо**: Разбить на структурированные блоки (XML-теги или
Markdown-заголовки). Ключевые инструкции — в начале и в конце
(Flash лучше запоминает края промпта).

---

## AP-12: Доверие к ответу без валидации [ MEDIUM ]

**Проблема**: Агент вернул JSON — но он может содержать лишние ключи,
неправильные типы или пропущенные обязательные поля.

**Хорошо**: Всегда валидируй ответ на бэкенде через Zod.
В Antigravity — проверяй ответ субагента перед использованием.

## AP-19: Игнорирование оригиналов спецификаций (Secondary Source Trap) [ CRITICAL ]

**Проблема**: Агенту или Оркестратору передается только краткий пересказ, саммари или вторичный конспект, в то время как в репозитории/проекте существует подробная оригинальная спецификация (например, в `docs/`, `docs/consilium/`, PRD, ТЗ). Агент упускает критические детали, граничные условия и формулы.

**Плохо**:
```
Передай агенту: "Реализуй Спринт 6.7 на основе kontext/07.md".
(При этом файл docs/consilium/sprint_6_7_autopilot.md на 500 строк не включен в источники).
```

**Хорошо**:
```
📥 ОБЯЗАТЕЛЬНЫЙ ПЕРВОИСТОЧНИК (MANDATORY READ):
file:///c:/Project/docs/consilium/sprint_6_7_autopilot.md
Сначала прочитай оригинальную спецификацию через view_file от первой до последней строки.
Каждое архитектурное решение сверяй с первоисточником.
Вторичные конспекты (kontext/NN_*.md) используй только как контекст сессии, но не как замену ТЗ!
```

## AP-20: Sequential Launch Trap (Ловушка последовательного запуска) [ HIGH ]

**Проблема**: Оркестратор запускает агентов по одному, ожидая ответа каждого перед запуском следующего, хотя их задачи независимы. Это замедляет работу в несколько раз.

**Плохо**:
```json
invoke_subagent({"Subagents": [{"Role": "Agent 1", "Prompt": "..."}]})
// ждет ответа...
invoke_subagent({"Subagents": [{"Role": "Agent 2", "Prompt": "..."}]})
// ждет ответа...
```

**Хорошо**:
Использовать `Subagents[]` массив и таблицу зависимостей `(Задача | Зависит от | Волна)` для параллельного запуска.
```json
invoke_subagent({
  "Subagents": [
    {"Role": "Agent 1", "Prompt": "..."},
    {"Role": "Agent 2", "Prompt": "..."},
    {"Role": "Agent 3", "Prompt": "..."}
  ]
})
```

## AP-21: Single-Writer Violation (Конфликт параллельной записи) [ CRITICAL ]

**Проблема**: Два или более параллельных агента модифицируют один и тот же файл. Файловая система применяет Last-Write-Wins — правки первого агента бесследно уничтожаются.

**Плохо**:
```
Волна 1: Agent-A пишет в src/types/shared.ts, Agent-B тоже пишет в src/types/shared.ts
→ Результат: правки Agent-A потеряны.
```

**Хорошо**:
```
📁 SINGLE-WRITER RULE:
- Каждый параллельный агент пишет ТОЛЬКО в свою изолированную папку (src/modules/<agent>/).
- Общие файлы (shared.ts, package.json, schema.prisma) модифицирует ТОЛЬКО оркестратор после завершения волны.
- Для параллельного кодинга используй Workspace: "branch" (изолированный git worktree).
```

## AP-22: Zombie Wave Progression (Запуск волны без проверки предшественника) [ CRITICAL ]

**Проблема**: Оркестратор запускает Волну 2, не убедившись что Волна 1 завершилась успешно. Агенты Волны 2 получают промпты с несуществующими файлами или галлюцинированными данными.

**Плохо**:
```
Волна 1: DB-Scout крэшнул, /scratch/db_report.md не создан.
Волна 2: Security-Analyst получает MANDATORY READ: /scratch/db_report.md → FileNotFoundError.
```

**Хорошо**:
```
⛔ DEPENDENCY GATE (между волнами):
1. Проверить: все ли агенты Волны N ответили.
2. Проверить: нет ли статуса [ BLOCKER ].
3. Проверить: все ли ожидаемые артефакты существуют на диске.
4. Если предшественник упал → CANCELED_BY_DEPENDENCY для зависимых задач.
5. Git checkpoint: git commit -m "chore(swarm): wave N complete".
```

## AP-23: Research Agent Write Trap (Запись файлов Read-Only агентом) [ CRITICAL ]

**Проблема**: Агенту с `TypeName: "research"` (read-only, без инструментов записи) поручается сохранить отчёт в файл. Агент физически не может создать файл и падает с ошибкой инструмента.

**Плохо**:
```json
{"TypeName": "research", "Prompt": "Проведи аудит. Результат сохрани в /scratch/audit.md"}
```

**Хорошо** (вариант A — возврат через сообщение):
```json
{"TypeName": "research", "Prompt": "Проведи аудит. Верни результат в ответном сообщении. Формат: # Audit Report + список находок."}
```

**Хорошо** (вариант B — агент с правами записи):
```json
{"TypeName": "self", "Prompt": "Проведи аудит. Результат сохрани в /scratch/audit.md и верни путь."}
```

## AP-24: Missing Circuit Breaker (Отсутствие защиты от каскадных ретраев) [ HIGH ]

**Проблема**: Агенты работают с внешними API (search_web, Playwright, Яндекс.Директ) без инструкций по обработке ошибок 429/500. При сбое API 5 параллельных агентов шлют повторные запросы, сжигая токены и бюджет.

**Плохо**:
```
"Prompt": "Собери данные с 10 сайтов через search_web."
// Нет инструкций: что делать при 429? При 500? При таймауте?
```

**Хорошо**:
```
"Prompt": "Собери данные с 10 сайтов через search_web. При ошибке API 429/500 — СТОП, не шли повторные запросы. Верни статус [ BLOCKER ] API Error с описанием. Оркестратор решит."
```

## AP-25: No Heartbeat Timeout (Отсутствие тайм-аута на субагента) [ MEDIUM ]

**Проблема**: Оркестратор запускает субагентов и ждёт Reactive Wakeup бесконечно. Если субагент завис — оркестратор тоже зависает навечно.

**Плохо**:
```
invoke_subagent({"Subagents": [...]})  // Запустили и ждём...
// Субагент завис на 47 минуте. Оркестратор мёртв.
```

**Хорошо**:
```
invoke_subagent({"Subagents": [...]})  // Запустили
schedule(DurationSeconds=900, Prompt="Проверь субагентов", TimerCondition="any")
// 15 минут — если нет ответа, проверь и kill зависших.
```

## AP-26: Unstructured Handoff (Неструктурированная передача результата) [ MEDIUM ]

**Проблема**: Субагент возвращает свободный текст без структуры. Оркестратор тратит токены и внимание на парсинг, теряет находки и блокеры в потоке текста.

**Плохо**:
```
subagent → "Ну в общем я посмотрел код и там есть проблемы с типами..."
```

**Хорошо**:
```
subagent → "# Status: [ RISK ]\n## Резюме\nОбнаружены 3 нарушения типобезопасности.\n## Находки\n- [ RISK ] Implicit any в auth.ts#L45 — источник: auth.ts\n..."
```
