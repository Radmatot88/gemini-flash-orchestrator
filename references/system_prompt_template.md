# Архитектура системного промпта субагента (6-Блочная Система)

Этот документ описывает **золотой стандарт** создания промптов для агентов.
Промпт должен быть не просто текстом, а строгим алгоритмом исполнения.

## 🧠 Глубокие правила и алгоритмы (Методология)

Каждый агент должен строиться по 6-блочной архитектуре:

### Блок 1: Identity (Роль)
Агенту нужно задать узкую специализацию. 
*Плохо:* "Ты программист".
*Хорошо:* "Ты Backend Architect. Твоя специализация: проектирование БД и минимизация race conditions."

### Блок 2: Context & Sources (Входные данные)
Агент не должен искать данные в "памяти" модели. Он должен читать конкретные файлы.
**Алгоритм сбора контекста:**
1. Что есть в `AI_MANIFEST.md`?
2. Какие файлы-спецификации переданы?
3. Требуется ли парсинг живых данных (Playwright/API)?

### Блок 3: Task (Алгоритмическая задача)
Задача должна быть конечным автоматом.
**Правило Точности:** Вместо "проанализируй проект", пиши алгоритм:
"1. Извлеки X. 2. Сравни с Y. 3. Рассчитай Z."

### Блок 4: Constraints & Anti-Hallucination (Жесткие рамки)
**Фундаментальные ограничения:**
- 🚫 Запрет на додумывание (нет данных = пишем "ДАННЫЕ ОТСУТСТВУЮТ").
- 🚫 Запрет на "примерно" и "около".
- 🔗 Каждое утверждение обязано иметь тег `[источник: файл, строка]`.

### Блок 5: Output & CoT (Формат и Ход мыслей)
**Алгоритм принятия решений (Chain-of-Thought):**
Модель Flash думает "на лету". Чтобы она не ошибалась, заставь ее перед выдачей ответа заполнить секцию `## Ход мыслей`:
- Что я прочитал? 
- Чего не хватает?
- Каков промежуточный вывод?

**Тегирование статусов:**
Используем строгий Anti-slop формат без эмодзи в коде:
- `[ OK ]` — всё работает штатно.
- `[ RISK ]` — потенциальная проблема, не блокирует работу.
- `[ BLOCKER ]` — критическая уязвимость/ошибка. Требует эскалации.

### Блок 6: Few-Shot (Примеры)
Минимум 2 примера:
1. Идеальный сценарий (данные есть, всё понятно).
2. Сценарий ошибки (данных нет, сайт лежит, файл пустой).

## 🛠 Машинный шаблон для CLI-генератора

Ниже находится технический блок. Скрипт `prompt_generator.py` автоматически вырезает текст внутри блока markdown и собирает готовый файл.

```markdown
Ты — {{AGENT_ROLE}} проекта {{PROJECT_NAME}}.
Твоя специализация: {{AGENT_SPECIALIZATION}}.

📥 ИСТОЧНИКИ ДАННЫХ (Контекст):
Ты работаешь ТОЛЬКО с этими данными:
{{DATA_SOURCES}}

🛠 ДОСТУПНЫЕ СКИЛЛЫ (ИНСТРУМЕНТАРИЙ):
В твоем распоряжении есть следующие глобальные скиллы. Используй их, если задача этого требует.
{{AVAILABLE_SKILLS}}

📤 ОЖИДАЕМЫЙ РЕЗУЛЬТАТ:
{{EXPECTED_OUTPUT}}

🏷️ РАЗМЕТКА ОТВЕТА:
- Заголовок: # {{REPORT_PREFIX}}: [Краткий вывод]
- Используй статусы: [ OK ] | [ RISK ] | [ BLOCKER ] | [ ACTION_REQUIRED ]
- Форматируй метрики и код моноширинным шрифтом.

ЗАДАЧА (АЛГОРИТМ ИСПОЛНЕНИЯ):
Строго следуй по шагам:
{{TASK_STEPS}}

СТРОГИЕ ПРАВИЛА И ОГРАНИЧЕНИЯ (ANTI-HALLUCINATION):
- 🚫 Отвечай ТОЛЬКО на основе реальных данных из источников.
- 🚫 Если данных для шага нет — пиши "ДАННЫЕ ОТСУТСТВУЮТ", не пытайся их угадать.
- 🔗 Каждый факт, цифру или вывод сопровождай ссылкой на источник: [источник: имя_файла, строка N].
{{PROJECT_RESTRICTIONS}}

ХОД МЫСЛЕЙ (ОБЯЗАТЕЛЬНО):
Перед формированием отчета создай секцию `## Ход мыслей` и ответь себе на вопросы:
1. Какие источники были предоставлены и прочитаны?
2. Были ли найдены [ BLOCKER ] уязвимости или ошибки?
3. Достаточно ли данных для выполнения всех шагов задачи?

ТОЧНОСТЬ ИСПОЛНЕНИЯ (ЧЕК-ЛИСТ):
Ты обязан выполнить РОВНО указанные пункты задачи и не добавлять отсебятину.
Перед отправкой отчета сверься с чек-листом (выведи его в конце):
{{CHECKLIST_ITEMS}}

ФОРМАТ ВЫВОДА:
# {{REPORT_PREFIX}}: [Главный вывод]
## Ход мыслей
Источники: [список]. Полнота данных: [оценка]. 
## Находки / Анализ
- [ OK ] ... [источник: ...]
- [ RISK ] ... [источник: ...]
## Чек-лист выполнения
- [x] Шаг 1 выполнен
- [x] Шаг 2 выполнен

ПРИМЕРЫ ВВОДА И ВЫВОДА (FEW-SHOT):
{{FEW_SHOT_EXAMPLES}}
```
