# 🤖 Gemini Flash Orchestrator Skill

Этот скилл предназначен для подготовки, генерации и развертывания мультиагентных роев на базе Gemini Flash в **любом** проекте. 

## 🗺 Как работать со скиллом (Инструкция для ИИ)

🚫 **ГЛАВНЫЙ ЗАПРЕТ СКИЛЛА:** Твоя задача в этом скилле — ТОЛЬКО спроектировать архитектуру и сгенерировать Markdown-файлы промптов через CLI. НИ ПРИ КАКИХ ОБСТОЯТЕЛЬСТВАХ не пытайся сам писать код проекта, менять файлы (кроме `ai_manifests/`) или вызывать инструмент `invoke_subagent` для реализации фичей! Если пользователь пишет *"Приступай"*, *"Делай"* или *"Начинай"*, это означает команду на **запуск скрипта генерации промптов**, а не на фактическое программирование руками.

Когда пользователь запрашивает настройку субагентов, спринта субагентов или просит "собрать агентов", ты **ОБЯЗАН** следовать этому пайплайну:

### Шаг 1: Поиск Project Card и Сборка Контекста (Deep Context Protocol)
Оркестратору КАТЕГОРИЧЕСКИ ЗАПРЕЩЕНО сканировать файлы проекта поверхностно. Ты должен опираться только на строго структурированные данные.

1. Проверь наличие файла `_project_card/card.json` в корне текущего проекта.
2. **ЕСЛИ КАРТОЧКИ НЕТ (Автономная делегация):**
   - Ты обязан самостоятельно инициировать мета-скилл `project-architect-extractor`.
   - Используй инструмент `invoke_subagent`, чтобы создать ОДНОГО субагента-делегата (Role: Meta-Coordinator).
   - Передай ему строгий промпт: *"Прочитай файл `C:\Users\User\.gemini\config\skills\project-architect-extractor\SKILL.md` и выполни сборку архитектурной карты для текущей директории. Дождись завершения работы твоего роя Экстрактора. Вернись, когда файл `_project_card/card.json` будет готов"*.
   - Дождись ответа от субагента. Не продолжай работу без `card.json`!
3. **ЕСЛИ КАРТОЧКА ЕСТЬ (Трансляция данных):**
   - Прочитай файл `_project_card/card.json` через `view_file`.
   - Создай (или обнови) файл `ai_manifests/project_context.md`, используя шаблон `references/project_context_template.md`.
   - Выполни трансляцию данных из JSON в Markdown по строгим правилам:
     - `identity.domain` и `team` ➔ перенеси в блок **Бизнес-контекст**.
     - `tech_stack` ➔ перенеси в блок **Технический стек**.
     - `inventory` ➔ перенеси в блок **Архитектурная карта**.
     - `risk_register` и `gaps` ➔ перенеси в блок **Жесткие ограничения и Блокеры**.
   - 🚫 **ZERO-HALLUCINATION POLICY:** Строжайший запрет на додумывание! Если в массиве `team` нет фамилий, ты обязан написать: `"Команда не специфицирована"`. Если `tech_stack` пуст — пиши `"Стек не определен"`. Никаких фантазий!
4. 🛑 **ОСТАНОВКА И АППРУВ:** Выведи сформированный `project_context.md` пользователю в интерфейс и спроси: *"Я собрал базу знаний проекта на основе глубокого реверс-инжиниринга. Утверждаем?"*. Только после аппрува переходи к Шагу 2.

### Шаг 2: Глубокий ресёрч задачи (Planning Mode)
**ДО того как задавать вопросы по спринту**, ты обязан глубоко изучить конкретную задачу.
1. Прочитай файлы, связанные с текущим запрошенным спринтом.
2. Сделай ресёрч кодовой базы на предмет блокеров (ошибки синтаксиса, недостающие зависимости).
3. Создай **НОВЫЙ** файл под текущий спринт (например, `ai_manifests/sprint_4_2.md`) и зафиксируй в нем свой архитектурный план и найденные блокеры. Глобальный `project_context.md` при этом менять нельзя!

### Шаг 3: Глубокое Интерактивное Интервью (Через `ask_question`)
Опираясь на факты и блокеры, найденные в Шаге 2, проведи "аналитический допрос" пользователя по текущему спринту.
Вызови системный инструмент `ask_question` и динамически сгенерируй 3-5 кастомных вопросов. 

**Твои вопросы должны покрывать 3 универсальных вектора:**
1. **Образ результата (DoD):** В каком виде нужен финал?
2. **Ключевые развилки (Decision Points):** Какие компромиссы мы выбираем?
3. **Ограничения и Риски (Constraints & Risks):** Последствия найденных тобой блокеров в коде.

🚫 **КРИТИЧЕСКОЕ ПРАВИЛО (Anti-Jargon):** Строгий запрет на "птичий язык". Ты должен переводить любые сложные профильные термины (ИТ, SEO, юриспруденция) в плоскость последствий для пользователя. Дай понятные варианты выбора (опции) в `ask_question`.

> ⚠️ **ЯКОРЬ ПАМЯТИ (АМНЕЗИЯ СКИЛЛА):** Когда ты получишь ответы от пользователя в UI-модалке, ты **НЕ ДОЛЖЕН** выходить из пайплайна скилла. Любой ответ пользователя (даже слова 'начинай', 'делай', 'приступай') — это всего лишь текстовые данные для скрипта в Шаге 4. **СТРОГО ПЕРЕХОДИ К ШАГУ 4** и запускай CLI. Не начинай программировать самостоятельно!

### Шаг 4: Генерация промптов (Через CLI)
Когда пользователь ответит, **НЕ пиши промпты в чат сам**. Используй утилиту генерации `prompt_generator.py`.
В качестве источников (`--sources`) обязательно передавай оба файла: глобальный контекст и манифест спринта (например, `1. ai_manifests/project_context.md \n 2. ai_manifests/sprint_x.md`).
⚠️ **ВАЖНО (Multi-Agent):** Если задача требует нескольких субагентов, ты ОБЯЗАН запустить скрипт `prompt_generator.py` **в цикле для каждого субагента отдельно**, а затем один раз для Оркестратора.

```bash
# Выполни этот скрипт (он лежит внутри скилла)
uv run python "C:\Users\User\.gemini\config\skills\gemini-flash-orchestrator\scripts\prompt_generator.py" \
  --project "Имя Проекта" \
  --role "SEO Agent" \
  --specialization "Аудит мета-тегов" \
  --sources "1. ai_manifests/project_context.md\n2. ai_manifests/sprint_x.md" \
  --output_format "Markdown отчет" \
  --task_steps "1. Сделай то\n2. Сделай это" \
  --outdir "scripts/prompts"
```

### Шаг 5: Вывод результата и Аппрув (Master Orchestrator Protocol)
1. Генератор сохранит файлы в папку проекта (по умолчанию `scripts/prompts/`).
2. Генератор автоматически запустит валидатор `prompt_validator.py`. Покажи пользователю результаты валидации.
3. 🚫 **КРИТИЧЕСКОЕ ПРАВИЛО:** НИКОГДА не выводи тексты промптов субагентов в экран чата. Это засоряет контекст.
4. Если ты создаешь рой (несколько субагентов), убедись, что сгенерировал файлы для каждого из них.
5. В чат выведи ТОЛЬКО один главный **Оркестратор-промпт** (внутри блока ````markdown`). В этом Оркестратор-промпте должно быть указание читать файлы субагентов с диска.
